# ADR-0007: Shared vault storage, scaling, and the runner registry

**Status:** Partially implemented (10.07.2026)
**Decision-makers:** Repo owner (Jonas), early tester (Olli, @OlArtTro)

> **Implementation (10.07.2026):** The `org:<name>` storage tier (a dedicated private Git vault repo on
> the org's Git host) and its sync ship via `scripts/memory-sync.sh` (`pull`/`promote`, read-only
> overlay, discipline gate). Still **proposed**: the scaling staircase (frontmatter-filter → index →
> search), the tenant tier, and the runner registry.

## Context

ADR-0006 defines the layered scope model and its rules but not **where the shared tiers physically
live** or **how loading scales** as the shared knowledge grows. This ADR specifies storage, the scaling
staircase, the tenant tier, and the runner registry that the claiming protocol (ADR-0005) needs.

## Decision

### Storage per tier

| Scope | Where it lives |
|---|---|
| `framework` | the public CCPR repo (Git) |
| `org:<name>` | a dedicated **vault repo** (Git), private to the org, on the org's Git host |
| `product:<name>` | the product's repo/org |
| `project:<id>` | the project repo (`docs/`), as today |

### The vault is just a Git repo

- **Markdown + wikilinks + typed frontmatter** — the same minimal vault model, shared instead of local.
  **No new service, no vector store (YAGNI).**
- Synced by **Git pull** over the org's network; a **local clone is the offline cache**.
- **Access control falls out of the Git host's org structure** — an org-per-client layout already
  isolates project scopes; the org vault lives in the org. No bespoke auth.

### Scaling staircase (adopt in this order, not preemptively)

1. **Frontmatter as filter (now).** CCPR never loads the whole vault — it loads the **intersection of
   scope / tags / status** relevant to the current phase. (Consistent with typed-frontmatter edges +
   agentic traversal, not a graph DB / vector stack.)
2. **Generated index files.** A per-topic catalog (title, one-liner, tags), regenerated by a script on
   each vault commit; CCPR reads the catalog first, then fetches specifically.
3. **A search index as a derived artifact — only on real need** (e.g. SQLite-FTS or embeddings), built
   from the vault, regenerable. **Direction is always Git → index, never the reverse.**

### Tenant tier

For an agency serving many clients: **one vault repo per tenant** in that tenant's Git org, with scope
`tenant:<id>` slotting into the model (ADR-0006). Isolation stays free via org permissions —
structural scaling, not a monolith.

### Lifecycle

Review the shared (`org`) instincts on a cadence (per cycle/retro): merge duplicates, mark stale ones
`status: deprecated` rather than deleting them (traceability).

### The runner registry

The claiming protocol (ADR-0005) relies only on the `runner:<id>` string. A **runner registry** maps
each `runner:<id>` to its dispatch metadata — owner, machine/hardware, subscription/capacity — for
**manual runner routing**. It is **deployment-specific config** (a small file in the org vault or the
org's infra repo), **not a public-framework artifact**: the framework consumes the id; the registry is
where a team records what each id means.

## Consequences

- The `org` tier has a **boring, concrete home** — a Git repo — so there is no new infrastructure to
  run or secure.
- **Access control is inherited** from the Git host.
- **Loading scales by adding derived, regenerable artifacts** (index, then search) only on evidence,
  always sourced from Git.
- **Multi-tenant is structural** — a repo per tenant — not a permissions maze in one store.
- The **runner registry** gives the claiming protocol its `id → machine` mapping without leaking a
  deployment concern into the framework.

## Alternatives considered

- **A dedicated knowledge service / vector DB from the start:** rejected — YAGNI; a Git repo +
  frontmatter filtering covers the current scale. Add a derived index only when retrieval actually
  hurts.
- **The tracker's built-in wiki / knowledge base as the vault:** rejected. It has no PR-based
  de-customization gate, no Git versioning, and its content lives in the tracker instead of Git —
  which breaks the runtime overlay (ADR-0006) and the solo case. Hence the **three-way split**: work
  state → the tracker; machine-consumed knowledge (instincts, learnings, HANDOVER, Constitution) →
  Git; human companion docs (meeting notes, briefings, onboarding) → optionally the tracker wiki. **The
  wiki is never the source of truth for anything CCPR reads.**
- **Index / search as the source of truth:** rejected — always Git → index, never the reverse; a
  regenerable derived artifact cannot be authoritative.
