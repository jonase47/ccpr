Two residual items from WI-0014, neither a leak, both measured 19.08.2026.

(1) A destination beginning with a dash is accepted and published. Verified: "promote <src> --all" and "promote <src> -n" both exit 0 and create files literally named "--all" and "-n" in the shared tree. This is no longer a leak -- the WI-0014 guard made the checked string and the shipped string identical, so only the typed name is published -- but a file called "--all" in a shared repository is almost certainly a mistyped flag rather than an intended filename, and it will confuse every tool that later globs that directory. One case arm in require_file_destination refuses it. The reason it is not urgent: nothing unexpected is published, only something useless.

(2) Content-side deny matching is ASCII-only and un-normalised, while path matching was fixed in WI-0014 to normalise to NFC and fold non-ASCII case via python3. So a tenant name written in NFD inside a file's CONTENT, or differing only in non-ASCII case, still passes the content gate while the same string in a path is now caught. The asymmetry is deliberate and documented in the library: path matching runs once per file, content matching runs per line of every file, and escalating per line would cost a helper process per file across the whole sweep. Worth revisiting with a measurement rather than an assumption -- the cost may be acceptable now that the sweep is 283 files, and an asymmetric check is a rule a reader has to remember.
