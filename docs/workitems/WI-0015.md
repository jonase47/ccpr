Two symlink behaviours in artifact-gate.sh, both measured 18.08.2026 and both inert in this repo today (0 tracked symlinks), so neither blocked WI-0004.

(1) A dangling symlink vanishes from the scope silently. Built a repo with a tracked link pointing at a non-existent target and a configured deny name matching the LINK's own filename: "scanned 1 files, 0 findings", no skip line, exit 0. The name was never deny-checked and the scope shrank without saying so -- the same silent-shrink class the readable-file fix closed. Not a two-liner: the entry needs its own counter and summary line, otherwise the fix reproduces the defect it closes. Estimated ~6 code lines plus 3 tests.

(2) A resolving symlink is followed. A link to an in-repo target means that target is scanned twice; a link to an out-of-repo target is reported under a repo-relative path even though the target does not ship, which would fail a CI job over a file that is not an artifact.

Decide the intent first, then implement: the gate's subject is "what ships", and whether a symlink ships its target or merely its own name is a distribution question, not a scanning one. Check what install.sh does with symlinks under the FRAMEWORK directories before choosing.
